02.1 CASE STUDY — DESIGN SYSTEM

Cloudypedia

A lightweight design system built in parallel with a 48-hour product sprint — the tokens, components, and documentation pattern that let a 4-person team ship a coherent AI lesson-planning tool against the clock.

01 PROBLEM

A hackathon timeline doesn't leave room for a style guide — until it does.

With three parallel tracks and 48 hours on the clock, engineering couldn't wait on design decisions mid-build. Early screens were getting styled ad hoc — colors, spacing, and component states decided screen-by-screen — which meant every new screen risked drifting from the last, and every handoff meant re-explaining a decision verbally instead of pointing at a spec.

  • No shared color or type tokens — each new screen introduced values from scratch.
  • Core interaction states (loading, generated, editable) weren't defined once, so engineering was left guessing on edge cases.
  • Design and engineering were building simultaneously, with no shared source of truth to hand off from.
RESEARCH ARTIFACT PLACEHOLDER — swap in early ad hoc screens or a problem framing diagram

02 APPROACH

A minimal token set, defined once and referenced everywhere.

Before any screen got built, I locked the smallest possible set of shared values — just enough for engineering to move without stopping to ask design a question.

  • One accent color and a short neutral scale, set before any screen existed, so nothing needed a design review to greenlight a color.
  • A type scale — display for headlines, body for content, mono for system and status text — shared across every screen.
  • A spacing scale defined up front so engineering could estimate padding and gaps without pinging design mid-sprint.

03 COMPONENTS

One card, one button, one input — reused across the entire flow.

Rather than design bespoke UI for every step of the input → generate → edit flow, I built a small set of components with variants for each state they'd need to carry, then reused them end to end.

Before

Every screen mocked with one-off colors and spacing, decided in the moment. Engineering had to guess at states that weren't explicitly drawn.

After

A single input, card, and button component — each with defined default, loading, and generated states — referenced across every screen in the flow.

04 ARCHITECTURE

Documented the same way, every time.

Even under a hackathon deadline, every component page followed the same three-part structure — so engineering could self-serve instead of pinging design in Slack for every question.

05 OUTCOME

A system that held together long enough to pitch live.

Cloudypedia shipped as a working, demoable prototype by the end of the hackathon — every screen built from the same token set and component library, so the pitch felt like a coherent product rather than a stitched-together demo. The team pitched live to judges, walking through the generated-plan flow end to end, and got direct feedback from teachers on-site that validated the core mechanic: a first-draft plan a teacher would actually want to edit, not discard.
